先结合全部证据判断能否可靠形成测试用例，再返回结构化结果。不要输出分析过程。

## 信息完整性判断

只有满足以下条件时才能设置 `sufficient=true`：

1. 能确定需要验证的业务目标、角色、输入及外部可观察结果。
2. 读取到的代码与需求所在业务或技术边界存在实际关联。
3. 不存在会显著改变测试步骤和预期结果、但当前证据无法消解的歧义或冲突。
4. 能使用不超过 20 条、不过度拆散的独立用例可靠覆盖需求。

需求描述尚未实现的新能力、当前代码尚无最终行为，不能单独作为失败理由。代码能够证明入口、术语或扩展边界即可。

信息不足时设置 `sufficient=false`、`testCases=[]`，并在 `failureReason` 中具体说明需要补充什么、哪里冲突或为什么需要拆分需求。

4. 同一已有用例最多返回一条变更。不得用“删除旧用例 + 新增相似用例”代替可以直接表达的更新。
5. 使用满足可靠覆盖所需的最少集合，不得机械地把每条验收标准转换成一条用例。
6. 每条用例只覆盖一个完整业务场景；相关的输入、动作和结果应保留在同一条端到端流程中。
7. `name` 使用简洁短标题，尽量控制在 15 个字以内，只保留业务对象、关键条件和结果；确有必要时可以适当超过，但不得包含编号或复述完整步骤。
8. `groupId` 只能使用“当前项目可选分组”中给出的精确 ID。新增用例无法明确归类时返回 `null`；更新用例无需改变分组时沿用已有分组 ID。
9. `preconditions` 使用普通文本，列出该用例独立执行所需的账号、数据和初始状态；没有必要条件时返回空字符串。
10. `steps` 使用从 1 开始的连续编号普通文本。步骤应包含明确输入和操作，并在流程结尾验证业务结果及必要的用户或数据状态。
11. 不使用 Markdown 标题、表格或代码块。
12. 不写 CSS 选择器、DOM、坐标、按钮位置、页面布局、组件、函数、接口或数据库实现。
13. 除非需求明确规定，不引用精确提示文案，使用稳定的业务含义。
14. 多条用例不得重复，也不得只替换一组等价输入后重复同一场景。
15. 项目变量只能从“当前项目可用变量”中选择，不得虚构变量或字段。语义明确匹配时应使用变量引用：标量使用 `${NAME}`，对象字段使用 `${NAME.field}`。
16. 正向业务场景需要先登录时，使用一个包含 `username` 和敏感 `password` 字段的账号对象（例如“使用 `${ADMIN}` 登录”）；登录失败等认证场景应引用 `${ADMIN.username}` 和明确的错误测试数据，不得使用完整账号对象触发预登录。
17. 一条用例最多使用一个完整账号对象；无法确定应使用哪个现有变量时，不要猜测，保留明确的业务测试数据描述。
